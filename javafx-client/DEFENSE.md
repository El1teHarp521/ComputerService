# Шпаргалка к защите КР2

Ответы на все пункты раздела ТЗ «На защите необходимо уметь объяснить» + порядок демонстрации.
Каждый участник должен уметь ответить на любой вопрос — спрашивают вразнобой.

---

## Порядок демонстрации (7–10 минут)

1. **Запуск:** Docker с PostgreSQL → `mvn javafx:run` → окно с 10 заявками.
2. **CRUD:** добавить заявку (клиент выбирается из списка, стоимость вводится сразу) → изменить двойным щелчком → удалить (показать подтверждение).
3. **Поиск, фильтры, сортировка:** ввести «ноутбук» → добавить фильтр «В ремонте» (условия комбинируются) → сортировка «Стоимость: по убыванию» → «Сбросить».
4. **Валидация:** в форме клиента ввести телефон `abc` и пустое ФИО → показать понятное сообщение; удалить клиента с заявками → показать правило.
5. **Связанные данные:** вкладка «Клиенты» → выбрать клиента → снизу его заявки; панель «Сведения о заявке» с контактами клиента.
6. **Статистика:** вкладка «Статистика» — показатели и диаграмма.
7. **Экспорт:** отфильтровать (например, «Выполнена») → «Экспорт в Excel» → открыть файл: в нём только отфильтрованные строки.
8. Показать `mvn test` (30 тестов, без базы данных).

## Вопросы из ТЗ

### Как запускается готовая система через Docker и как проверяется состояние PostgreSQL и backend?
(Это демо-архив `student-hub-suite`, не наш проект.) Порядок всегда один:
1. Запустить Docker Desktop, дождаться состояния Running.
2. В корне архива (там лежит `.env`): `powershell -ExecutionPolicy Bypass -File .\backend\start-compose.ps1`
   или `docker compose --env-file .env -f backend/docker-compose.yml up -d --wait`.
   Compose поднимает два контейнера: **PostgreSQL** и **Spring Boot backend**; параметры берутся из `.env`.
   Флаг `--wait` ждёт, пока пройдут healthcheck'и контейнеров.
3. Проверка: контейнеры `Running` и healthy (`docker ps`), открывается `http://localhost:8080/` (веб-интерфейс)
   и `http://localhost:8080/actuator/health` (состояние backend).
4. Только после этого — `javafx-client` из архива (`mvn javafx:run`), он ходит в REST API `http://127.0.0.1:8080/api`.
5. Остановка: `docker compose --env-file .env -f backend/docker-compose.yml down` (данные сохраняются; том не удалять).

**Важное отличие:** демо-клиент работает через REST API, а **наш** клиент подключается к PostgreSQL напрямую по JDBC —
так требует ТЗ КР2. В нашей базе используется порт 5432, у демо-системы — 55432 (конфликта нет).

### Как запускается JavaFX-приложение?
`mvn javafx:run` → плагин стартует `ComputerServiceLauncher.main()` → тот вызывает `Application.launch(ComputerServiceFxApp.class)`
→ JavaFX создаёт поток интерфейса и вызывает `ComputerServiceFxApp.start(Stage)`. В `start()` загружается `MainView.fxml`,
создаётся `Scene`, окно показывается. Отдельный `Launcher` нужен, чтобы запуск из IDE работал, когда JavaFX
подключён как обычная библиотека (иначе ошибка «JavaFX runtime components are missing»).

### Что такое Stage, Scene и Node?
- **Stage** — окно операционной системы (у нас: главное окно и диалоговые формы).
- **Scene** — содержимое окна: дерево элементов, загруженное из FXML. У каждого `Stage` одна `Scene` в каждый момент.
- **Node** — любой элемент дерева: кнопка, таблица, панель, подпись. Корень сцены — тоже `Node` (`BorderPane` в `MainView.fxml`).

Иерархия: `Stage` → `Scene` → корневой `Node` → вложенные `Node`.

### Зачем используется FXML?
Чтобы **отделить внешний вид от логики**: разметка окна лежит в `MainView.fxml`, поведение — в `MainController`.
Интерфейс можно менять, не трогая код, а код — не трогая разметку; разметку можно открыть в SceneBuilder.
Оформление (цвета, шрифты) вынесено ещё глубже — в `app.css`.

### Как FXML связан с Controller?
Три механизма:
1. `fx:controller="…MainController"` в корне FXML — `FXMLLoader` сам создаёт объект этого класса.
2. `fx:id="requestsTable"` в разметке ↔ поле `@FXML private TableView<…> requestsTable` в контроллере (совпадение по имени) —
   так контроллер получает доступ к элементам.
3. `onAction="#onSearch"` в разметке ↔ метод `@FXML private void onSearch()` — это обработчик события.

После внедрения полей `FXMLLoader` вызывает `@FXML initialize()` — там настраиваются таблицы и запускается первая загрузка данных.

### Как обновляются данные в TableView?
`TableView` связана с `ObservableList` (`requestsTable.setItems(requestsData)`). Любое изменение списка —
`requestsData.setAll(новыеДанные)` — таблица замечает сама и перерисовывается. Обновлять строки вручную не нужно.
Данные приходят из базы в **фоновом потоке**, а `setAll` вызывается уже в потоке интерфейса (`FxTasks`).
После сохранения/удаления вызывается `refreshAll()`; выделенная строка восстанавливается по id (`reselect`).

### Зачем используется ObservableList?
Обычный `ArrayList` не умеет сообщать об изменениях. `ObservableList` умеет: у него есть слушатели, на которые
подписан `TableView`. Поэтому список — это **источник данных**, а таблица — только его отображение.

### Где находится бизнес-логика?
В `service/`: `ClientService`, `RepairRequestService`, `Validation`. Правила — обязательность и длины полей, формат телефона и email,
уникальность телефона/email, стоимость ≥ 0 и ≤ предела, запрет менять статус у выполненной/отменённой заявки, запрет
удалять клиента с заявками, корректный период дат. Контроллеры правил **не содержат** — только передают данные и показывают
результат. Поэтому те же правила работают и для консоли (КР1), и для JavaFX (КР2), и для REST API (КР3).

### Где выполняется работа с данными?
В `repository/` — классы `ClientRepositoryJdbc` и `RepairRequestRepositoryJdbc`. Это **единственное место с SQL**.
В обработчиках кнопок SQL нет (запрещено ТЗ). Подключение открывает `DatabaseManager`, параметры берутся из
`database.properties` — пароль не зашит в код.

### Как обрабатываются исключения?
Три собственных исключения: `BusinessException` (нарушено правило), `EntityNotFoundException` (нет записи),
`DatabaseException` (обёртка над `SQLException`). Схема:
- репозиторий ловит `SQLException` и бросает `DatabaseException`;
- сервис бросает `BusinessException` с понятным текстом (название поля + что исправить);
- `FxTasks.friendly()` превращает любое исключение в текст без stack trace;
- форма показывает текст **под полями**, окно остаётся открытым; прочие ошибки — диалог `Alert`.
Пустых `catch` нет, приложение не падает при ошибке ввода или недоступной БД.

### Как проверяются пользовательские данные?
Всё в `Validation` (вызывается из сервисов) **до** обращения к БД: пустые обязательные поля, длины (по `VARCHAR` в `schema.sql`),
формат телефона (10–15 цифр) и email, стоимость (не отрицательная, ≤ 99 999 999,99, ≤ 2 знаков после запятой),
период дат (с ≤ по), ссылка на существующего клиента (`EntityNotFoundException`), уникальность (телефон нормализуется к виду `+7…`,
email — к нижнему регистру, чтобы «одинаковые» значения считались дубликатом). В интерфейсе клиент выбирается из `ComboBox`,
а не вводится числом. Контроллер формы дополнительно ловит только `NumberFormatException` при разборе стоимости.

### Как реализован поиск и фильтрация?
`RepairRequestService.findFiltered(...)`: если задан текст — SQL-запрос `searchAnyField` (описание, устройство, ФИО клиента,
`LIKE` без учёта регистра, спецсимволы экранируются); иначе все заявки. Дальше **Stream API**: `.filter` по статусу, приоритету,
дате «с» и «по», `.sorted` выбранным `Comparator`. Условия соединяются через **И** — поэтому комбинируются. Любое
изменение условия в интерфейсе перезапускает загрузку; «устаревшие» ответы отбрасываются по номеру запроса.

### Как рассчитывается статистика?
`RepairRequestService.getStatistics()` один раз читает заявки и считает потоками: всего, активные, выполненные, отменённые,
доля высокого и срочного приоритета, за 30 дней, средняя/минимальная/максимальная стоимость, выручка по выполненным.
`countByStatus()` — количество по каждому статусу (`EnumMap`, нули тоже) для диаграммы. В интерфейсе значения выводятся
строками в `GridPane`, диаграмма — `BarChart`.

### Как выполняется экспорт?
Кнопка «Экспорт в Excel» берёт **текущее содержимое таблицы** (`requestsTable.getItems()` — то есть с учётом фильтров и
сортировки), путь спрашивает у пользователя через `FileChooser` (жёстких путей в коде нет), записывает файл через
Apache POI (`ExcelExporter`) в **фоновом потоке** и сообщает результат.

## Дополнительные вопросы, которые могут задать

**Зачем фоновые потоки (`FxTasks`)?** Интерфейс JavaFX работает в одном потоке. Запрос к БД в обработчике кнопки «замораживает»
окно (при недоступной БД — на секунды). `Task` выполняет работу в фоне, а результат возвращается в поток интерфейса.
Менять элементы интерфейса из фонового потока нельзя.

**Чем `Statement` отличается от `PreparedStatement`?** `PreparedStatement` принимает значения параметрами (`?`), а не склейкой строки:
защита от SQL-инъекций, правильное экранирование, возможность переиспользовать план запроса. У нас используется везде.

**Зачем интерфейсы репозиториев?** Сервис зависит от интерфейса, а не от JDBC. В тестах вместо базы подставляются
`FakeClientRepository` / `FakeRepairRequestRepository` (в памяти), поэтому 30 тестов выполняются за секунды без PostgreSQL.

**Какие связи в базе?** `repair_requests.client_id → clients.id` (один клиент — много заявок). В интерфейсе: вкладка «Клиенты»
показывает заявки выбранного клиента, панель «Сведения» — контакты клиента выбранной заявки.

**Что такое полиморфизм в проекте?** Сервисы работают с `ClientRepository`/`RepairRequestRepository`; фактический объект
(`…Jdbc` в приложении, `Fake…` в тестах) выбирается при создании. Ещё пример — `RequestSortOrder`: у каждого значения enum свой `Comparator`.

**Почему стоимость — `BigDecimal`, а не `double`?** Деньги нельзя хранить в двоичной дроби (0,1 + 0,2 ≠ 0,3); `BigDecimal` точен
и соответствует `NUMERIC(10,2)` в базе.

**Что делает `reselect`?** После перезагрузки таблицы `setAll` сбрасывает выделение; метод находит в новом списке строку с тем же id и выделяет её снова.
